[5] 异常定位：串口出现"刷屏/横幅重复几十次" —— 主机侧适配器故障，非固件缺陷
================================================================

现象（第一轮抓取）：
  · 复位前约 11 s，线路持续吐 0x40（'@'）约 114 KB
  · 复位后启动横幅的首行 `_/  _/ … _/_/_/` 被重复 64~72 次，且夹着一行
    由**两条不同横幅行拼成**的畸形文本（`\t   _/    _/` 后直接接第 4 行内容）
  · 另一轮里"串口"以 200+ KB/s 反复输出 `=== End PowerMgr ===` 片段

四条证据（全部指向主机侧）：

  1) 物理速率上限。9600 / 115200 / 230400 三种波特率下，收到的**内容完全相同**
     且速率都是 ~215~250 KB/s。115200 8N1 的物理上限是 11.52 KB/s 字节率，
     不可能被真实 UART 超越；波特率改到 9600 内容却不变，更说明它没经过 UART 接收。
  2) 因果否定。用 pyOCD 的 Python API **在同一进程里把核 halt 住并保持会话**，
     再采样串口：仍然 216354 B/s；`resume` 后 219202 B/s。**CPU 已停**，
     它不可能在发送。（若用 `pyocd cmd` 子进程做这个实验，进程退出可能自动
     resume，结论会不可信。）
  3) 设备侧直接否决。停机时读固件的日志环形缓冲 `log_ringbuf`：
     `size=1024 r_ptr=1003 w_ptr=1003 pending=0`，**5 秒内 r/w 指针一个字节都没动**。
     若固件真在以数百 KB/s 往外推，"写指针必然飞驰"。同时 PC 采样全部落在
     `prvIdleTask` / `xTaskResumeAll` / `vPortEnterCritical` / `vListInsert` ——
     系统处于空闲，不在打印路径上。
  4) 写入量断言。在 `main` 里 `bl log_raw` 的下一条（0x0800975C）下断点，
     复位后命中时读环形缓冲：`w_ptr = 225`，缓冲内容为
     **一份**横幅 + `\r\n`，其后全是 0x00。
     横幅字符数按源码算是 223，+ CRLF = **225**，与实测**恰好相等**。
     固件的每个 UART 字节都只来自 `lwrb_read()`（TXE ISR 或 `log_flush()`），
     **取走即删除** ⇒ 发出的字节数 ≤ 入队字节数。
     所以机器上不可能出现几十个横幅。

结论：`output/mhde_mainboard` 的日志子系统与固件功能均正常。
本次观察到的重复/刷屏全部来自 **FTDI(COM5) 适配器进入了"陈旧缓冲反复回放"的
卡死状态**（RX FIFO/驱动读取指针不前进，驱动按 USB 轮询节奏重复交付同一段内容）。

现场数据点：设备状态本身是正常的 ——
  `pnputil /enum-devices /class Ports` 显示 FTDI 为 `Status: Started`，
  没有黄叹号；但行为已不正常。

处置：
  · 软件侧复位设备需要管理员权限，本会话尝试失败：
    `pnputil /restart-device "FTDIBUS\VID_0403+PID_6001+A5069RR4A\0000"`
    → `Access is denied.`
  · **需要物理重新插拔 USB 适配器**（或以管理员身份重启该设备）。
  · 重插后再复跑 [3][4] 即可拿到干净日志。
  · 抓取脚本已加入自检与自愈：开工先 `reset_input_buffer()`；运行中若字节率
    超过 `baud/10 × 1.5` 即判定为主机侧回放，写告警并再 purge 一次
    （本轮触发了 11 次）。工具留在 `.workbuddy/tmp/serial_capture.py`。

----------------------------------------------------------------
[7.1] 缺陷 A：设备在块 0 之后**漏发 'C'**（设备侧，已修）
----------------------------------------------------------------
症状：第三方发送端在收到块 0 的 ACK 之后原地等到自己超时（60 s）才放弃。

裸探针（`.workbuddy/tmp/ym_probe.py`，不经任何自研发送代码）实测：
设备对块 0 的应答**只有 `0x06` 一个字节**，之后不再发 'C'。
而规范次序是：发 'C' → 收块 0 → **ACK** → **再发一个 'C'** → 收数据块。
YMODEM 的数据块超时基准就是那个第二个 'C'；漏掉它，外部发送端只能等自己的
上层超时。

为什么自研两侧从来没发现：`generator/fota_ymodem_sender.py::batch_plan()` 的
注释把块 0 写成"→ ACK"，设备也照这个实现 ⇒ **两侧错得一样**，L5 跨实现台架
同样用这份计划 ⇒ 9 个用例全绿。这是继 CRC 算法之后，同一类陷阱的第二次出现。

修复（四处同源）：
  · 真源 `generator/data/ymodem_format.json`：新增 `crc_after_header_ack: 1`
  · 上下文 `generator/context/bootloader_context.py`：投影 `hs_crc_after_header_ack`
    并在生成期拒绝"只让设备漏发"的退化
  · 设备 `templates/drivers/drv_fota_ymodem.c.j2::ym_handle_header()`：ACK 之后
    重起 tick 并发 'C'
  · 发送器 `generator/fota_ymodem_sender.py`：新增 `header_ack_response`，
    所有块 0 期望值改从它派生
  · 护栏：工程内新增
    `test_the_post_header_crc_request_is_sent_once_and_not_periodically`
    （用例总数 15→16，`grep -c RUN_TEST` 核过）；渲染层新增
    `test_the_header_path_sends_the_crc_request_after_the_ack`（含变异验证：
    删掉那句 'C' 后 L5 报 `device said [06 ] / protocol says [06 43 ]`）

----------------------------------------------------------------
[7.2] 缺陷 B：CLI 接收分发竞态（设备侧，已修）
----------------------------------------------------------------
症状：`fota ymodem\r` 紧接着的块 0 落在**同一个 RX 批次**里时，命令回
`Unknown command`，FOTA 状态静默停在 IDLE（last error 0，无 ymodem file 行）。

根因：`templates/drivers/drv_cli.c.j2` 的 `cli_task()` 对整批字节**只查一次**
`cli_rx_sink`，然后把整批交给行编辑器。命令执行时装上了 sink，但同批剩余的
块 0 字节已经被行编辑器吃掉。

判别过程：`.workbuddy/tmp/ym_idle_probe.py` 先证明设备本身正常（敲命令后
严格 3.05 s 一个 'C'、其余无字节），把怀疑范围从"接收状态机"缩到"命令分发"。

修复：抽出 `cli_dispatch_rx()`，**逐字节**重判当前接管者；sink 一装上就把
本批剩余部分整体交给它。护栏：
`generator/tests/test_template_render.py::test_cli_rx_dispatch_rechecks_the_handover_sink_per_byte`
（含变异验证）。

[7.3] 缺陷 C：信封 fw_version 与镜像头不一致 ⇒ 设备报 E_CRC(-19)（主机侧，已修）
----------------------------------------------------------------
这是本轮最有价值的一条：**它不是设备缺陷，是主机侧生成的补丁有问题**，
却伪装成一个"内容损坏"的设备错误。

症状（真机）：YMODEM 传输完整成功（第三方发送端 4.5 s 内传完 2388 B），
随后设备报 `[ERR] FOTA apply failed`，`fota status` 显示 `FOTA state: ERROR`
`last error: 0`，复位后仍是 v1.0.0，并留下 `hw2c_fault` 码 8
（`HW2C_FAULT_FOTA_APPLY`）。

取证受阻：`last error` 是 RAM 变量，复位即失；`.noinit` 的 fault 记录只存
**码**、不存细节；串口转录又把那条 119 B 日志的后 71 B 截断了（渲染器只留
前 48 B —— 见 §7.5）。**结论：这类"静默失败"的排查效率取决于诊断通道，
而三者当时都缺。**

破局办法（不依赖串口，也不依赖板子）：设备侧应用层是"纯逻辑 + 后端注入"
（无 HAL、无 `#ifdef TEST`），所以把**真机那份** `drv_fota_delta.c` 原样编到
主机上，喂**真实产物**重放。工具已固化进仓库（不再是一次性脚本）：
`tools/fota_apply_replay/apply_real.c`，用法见文件头注释。现场用的就是它：

  $ gcc -std=c99 -O1 -Wall -Wextra -Werror \
        -I output/mhde_mainboard/src/drivers \
        -I static/third_party/hpatch_lite \
        -I static/third_party/tinyuz/decompress \
        tools/fota_apply_replay/apply_real.c \
        output/mhde_mainboard/src/drivers/drv_fota_delta.c \
        static/third_party/hpatch_lite/hpatch_lite.c \
        static/third_party/tinyuz/decompress/tuz_dec.c -o apply_real
  $ ./apply_real output/mhde_mainboard/build/mhde_mainboard_crc.bin \
        .workbuddy/tmp/mhde_v101.h2cd \
        output/mhde_v101/build/mhde_v101_crc.bin
  → 结果 rc=-19 (E_CRC(-19)) derr=-19
     活动槽是否被改动: 未改动 ✓

定位：设备侧那 10 条校验逐条比对，前 3 条都过：
  · 槽 A 镜像头 magic ✓
  · `image_size + 208 == env.old_size`（118096+208 = 118304）✓
  · `live_crc == env.old_crc32`（0xDDF0D557，逐字节复算）✓
差异出在最后一步：
  · 新镜像头 `fw_version = 0x00000001`，而信封 `fw_version = 0x00000002`
  · 而 `crc_region` 从 magic(0xC8) 起、长度 = image_size + 8 ⇒
    **覆盖了 fw_version(0xCC) 那 4 字节**
  · 设备在 FLUSH 阶段把**信封里的**版本号写进新头部，再复算覆盖区 CRC
    ⇒ 必然与信封里预置的 `new_crc32`（按镜像头里的 1 算的）不符

即：`delta_tool build --version 2` 与镜像构建时的 `FW_VERSION`（默认 1）
对不上。**主机侧完全没有任何校验**，而设备侧的信息不足以区分"版本号不一致"
与"内容真损坏" —— 所以错误码把人往差分算法/Flash/传输上引。

修复（主机侧，不动固件）：
  · `generator/delta_tool.py::build()` 的 `fw_version` 改为**可选**，
    默认取**新镜像头里的值**；显式给出且不一致时直接 `ValueError`，
    消息里同时给出两个数字并点名真机症状 `FOTA_DELTA_E_CRC(-19)`
  · CLI `--version` 相应改为可选
  · 测试对齐：`test_delta_tool.py` 里 13 个用例原本在用"信封 1 / 镜像头 2"
    这个不一致组合 —— 之所以从未报错就是因为没有校验，这本身是该契约此前
    为空的证据
  · 新增 4 条护栏（`test_delta_tool.py` 第 2b 组）：默认值取自新镜像；
    不一致必须被拒且消息含两个数字；**CRC 覆盖区必须包含 fw_version**
    （把本组推理的前提钉住）；旧侧版本号不受约束（由 old_crc32 隐式钉住）
  · 新增设备侧护栏（`test_fota_delta_l6.py`）：把"信封 5 / 镜像头 5"与
    "只差信封版本号"的两份补丁分别喂给**设备侧真实代码**，断言
    `OK_RC=0` / `BAD_RC=-19`；并附变异验证（**同时**短路 7.5 与 7.6 两道
    CRC 闸门后才变为 0 —— 顺带确认该不变量有两道互相独立的闸门）

修复后同一条命令重放：
  → 结果 rc=0 derr=0
     目标槽 vs 新镜像: 逐字节一致（exp=118272）

✅ 已落地（2026-09-17 下午，见 §9）：镜像头的 `fw_version` 默认改为**派生自
`project.version`**（`major<<16|minor<<8|patch`），并保留 `-DFW_VERSION` /
环境变量 `FOTA_VERSION` 覆盖；需求进了 `docs/requirements.md` FR-14.7。

⚠️ 真实情况比上面那段"建议"更糟：按建议改完默认值之后，真机上版本号**还是不变**。
因为 `project.version` 从来就没走到 `build_context()` —— 见 §9 的缺陷 D。
"默认值常量"只是两个独立原因里的第二个；只改它等于什么都没改。

缺陷 D（本次新发现，**比缺陷 C 更靠前**）：`generate.py` 把软件层字段用
**手写白名单**搬进 `hw`：

[10] 缺陷 F：RTC `initial_time` 解析的静默出口（2026-09-17 续）
================================================================

起点不是上板，是用户问"开机 logo 怎么没了"。查证后确认横幅正常（§7.5 的
观察窗口问题），但用户贴的日志时间戳是 `11:01:30` 而墙上时钟是 15:48 ——
顺着"设备时钟从哪来"查下去，发现它来自配置里的固定初值：

    examples/mhde_mainboard/hardware.yaml:102  initial_time: "2026-09-17 10:00:00"
            ↓ 生成期解析
    output/mhde_v101/src/drivers/drv_rtc.c     sDate.Year=26, Month=9, Date=17, 10:00:00

`11:01:30` = `10:00:00` + uptime 3690 s，与日志严格自洽。真正的问题在
解析这块：**它从不报错**。

旧实现（`generator/context/builder.py` 预计算段）用手写 split：

    date_part, time_part = init_str.split(" ")
    y, mo, d = date_part.split("-")          # 字段位次完全不校验
    rtc_year = int(y) - 2000
    rtc_init_time = {"year": max(0, min(99, rtc_year)), "month": int(mo), ...}
    except (ValueError, AttributeError):
        pass                                  # malformed, use defaults

两个静默出口，都把"配置写错了"伪装成"配置成功了"：

  | 输入 | 旧实现的结果 | 后果 |
  |---|---|---|
  | `"17-09-2026 10:00:00"` | `year=17-2000=-1983` → clamp 成 0；`day=2026` | `sDate.Date = 2026` **原样进固件**（RTC 合法范围 1..31） |
  | `"2026/09/17 10:00:00"` | 静默 → 2000-01-01 00:00:00 | 用户以为设了 2026，实际差 26 年 |
  | `"2026-09-17 10:00"`（少秒） | 同上 | 同上 |

为什么值得单独记：`initial_time` 是**烤进固件**的常量，写错之后没有任何环节
能发现它 —— 唯一症状是"日志时间戳不对"，而那种现象天然会被当成 LSE 晶振 /
备份域问题去查硬件。与缺陷 D/E 同源：**配置错误要有出口，不许静默**。

修法（FR-13.6，与 FR-14.7 同原则）：
  · 先用 `^\d{4}-\d{1,2}-\d{1,2} \d{1,2}:\d{1,2}:\d{1,2}$` 校验**形状** ——
    月/日/时/分/秒允许不补零（人写的 YAML），但年份必须 4 位且在最前，
    因此 `DD-MM-YYYY` 被挡下；
  · 再用 `datetime(...)` 构造校验**日历合法性**（2 月 30 日、13 月、25 时）；
  · 年份必须落在 **2000..2099** —— 这是 RTC 日历自身的能力（只存 2 位年份）。
    **拒绝而不是钳制**：钳制后的值看起来是合法的，等于替 YAML 作者做了
    一个他看不到的决定；
  · 只有**省略**该字段时才用默认值（2000-01-01 00:00:00）。
